# 🧠 RAG 技术方案详解

> 版本：v3.3.1 · 更新日期：2026-08-17

## 1. 为什么需要高级 RAG

传统问答要么「纯 LLM」（容易幻觉、无知识依据），要么「TF-IDF 关键词检索」（无语义、召回差）。
本项目采用 **Hybrid RAG**：语义向量 + 关键词双路召回、多策略融合、可选交叉编码器精排，
兼顾**语义理解**与**精确匹配**，并用**来源引用**约束 LLM 输出，显著降低幻觉。

## 2. 检索链路总览

```
                        ┌───────────────────────────────┐
   query ─────────────►│       查询改写（多轮）          │
                        │   LLM 指代消解 / 意图补全      │
                        └───────────────┬───────────────┘
                                        │
              ┌─────────────────────────┼─────────────────────────┐
              │                         │                         │
   ┌──────────▼──────────┐   ┌──────────▼──────────┐            （可选）
   │   Dense 语义检索      │   │   Sparse 关键词检索   │            ┌──▼──────────┐
   │   bge 向量 → FAISS   │   │   jieba + BM25      │            │ 交叉编码器    │
   │   cosine top-k       │   │   top-k             │            │ bge-reranker │
   └──────────┬──────────┘   └──────────┬──────────┘            └──┬──────────┘
              │                         │                          │
              └────────────┬────────────┘                          │
                           │  RRF 融合 / 加权融合                    │
                           │  去重 + 归一                           │
                    ┌──────▼──────┐                                │
                    │  候选集 K    │────────────────────────────────┘
                    └──────┬──────┘
                           │ 取 top-N 送入 Prompt
                    ┌──────▼──────┐
                    │  LLM 生成    │
                    │  引用[来源N]  │
                    └─────────────┘
```

**关键参数**（`backend/core/config.py` / `.env`）：

| 参数 | 默认 | 含义 |
|------|------|------|
| `RAG_RETRIEVE_K` | 20 | 双路各粗召回条数 |
| `RAG_RERANK_K` | 6 | 融合后进入重排的候选数 |
| `RAG_TOP_K` | 4 | 最终送入 LLM 的知识条数 |
| `RAG_SIMILARITY_THRESHOLD` | 0.3 | 向量相似度阈值，低于判未命中 |
| `RAG_CHUNK_SIZE / OVERLAP` | 500 / 80 | 分块大小与重叠 |
| `RAG_USE_RRF` | true | 使用 RRF 融合（否则加权） |
| `RAG_USE_RERANKER` | false | 是否启用交叉编码器重排 |

## 3. 语义向量检索（Dense）

### 3.1 模型

- **`BAAI/bge-small-zh`**：中文检索专用双塔模型，输出 **512 维**向量。
- 针对中文场景优化，效果优于通用多语言模型，且体量小（约 100MB）、推理快。
- 支持 GPU 推理（项目环境为 CUDA），也可 CPU 运行。

### 3.2 指令前缀

BGE 系列要求**查询侧**添加指令前缀，否则效果明显下降：

```python
QUERY_INSTRUCTION = "为这个句子生成表示以用于检索相关文章："
query_vec = model.encode(QUERY_INSTRUCTION + query)
```

文档侧不加前缀（保持语义中立）。这是 BGE 官方推荐做法。

### 3.3 相似度计算

- 向量 L2 归一化后，**内积 = 余弦相似度**，因此用 `FAISS IndexFlatIP`（精确内积索引）一次搞定；
- 优点：无量化损失，小规模语料下精确且快。

### 3.4 工程细节

- **LRU 缓存**：重复查询的向量直接命中缓存，省一次模型推理；
- **批量编码**：入库时按 batch=32 批量编码，充分利用 GPU；
- **软删除**：删除文档不立即重建索引，搜索时过滤 active 集合；垃圾达到阈值自动重建压缩空洞。

## 4. 稀疏检索（Sparse / BM25）

### 4.1 为什么保留 BM25

向量检索擅长语义近义（"可乐" ↔ "碳酸饮料"），但对**专有名词、编号、精确词**不够敏感；
BM25 在字面匹配上更精准（如"可口可乐"、"GB 8537-2018"）。二者互补。

### 4.2 自研实现（零第三方依赖）

```python
score(q, d) = Σ  IDF(t) · f(t,d)·(k1+1) / ( f(t,d) + k1·(1-b + b·|d|/avgdl) )
IDF(t)      = ln( 1 + (N - df_t + 0.5) / (df_t + 0.5) )
```

- 分词：`jieba` 精确模式；
- 实现：`tf` 矩阵、`doc_len`、`doc_freq` 全部用 `numpy` 向量化，单次检索即矩阵运算；
- 标准参数 `k1=1.5, b=0.75`。

### 4.3 增量维护

文档增删后重建语料索引（当前规模下毫秒级），保证一致性与简单性。

## 5. 融合策略

### 5.1 RRF（Reciprocal Rank Fusion，默认）

对两路结果按**排序位次**融合，忽略分数绝对值：

```python
score(item) = Σ  1 / (RRF_K + rank_i)     # RRF_K = 60
```

**优点**：不同检索器的分数尺度不同，RRF 只依赖序关系，鲁棒、无需调权。

### 5.2 加权求和（可选）

```python
score = w_dense · norm(dense_score) + (1 - w_dense) · norm(sparse_score)
```

分数归一化到 [0,1] 后按权重融合，权重可调（`RAG_HYBRID_WEIGHT_DENSE`）。

### 5.3 去重与标记

同一 chunk 若双路都命中，标记 `method=hybrid`（前端展示召回路径，便于调试检索质量）。

## 6. 交叉编码器重排（Rerank，可选）

- **模型**：`BAAI/bge-reranker-base` 交叉编码器，将 (query, doc) 拼接后联合编码打分；
- **为什么更准**：双塔对 query/doc 独立编码，交互信息在后期才融合；交叉编码器全程交互，
  排序精度显著更高（尤其候选小、对首条精度敏感的问答场景）；
- **流程**：双路融合后取 `RERANK_K=6` 候选 → 逐对打分 → 重排序取 `TOP_K=4`；
- **降级**：模型未下载/加载失败时自动跳过重排（`reranker.failed=True`），不影响检索主链路。

> 💡 工程权衡：交叉编码器速度慢（需逐对推理），因此只对**小候选集**重排，兼顾精度与延迟。

## 7. 查询改写（Query Rewrite）

多轮对话中用户常问"它呢？""那这款呢？"——直接检索会漏掉核心实体。方案：

```
系统提示：把【对话历史】+【当前提问】改写为独立完整的检索查询
  （指代消解、补全实体、保留全部条件）
```

- 改写失败/无历史时**原样返回**，保证鲁棒；
- 可在 `.env` 用 `ENABLE_QUERY_REWRITE=false` 关闭（省一次 LLM 调用、降低延迟）。

## 8. 分块策略（Chunking）

| 类型 | 策略 |
|------|------|
| 内置饮料库 | 按"饮料块"（双换行分隔）整块切分，保留 8 个字段完整结构 |
| 通用文档 | 按空行切段落 → 超长段落按**句子边界**递归切分，相邻块保留 overlap |

- **句子边界优先**：避免切断语义；重叠窗口减少边界信息丢失；
- 输出统一为片段列表，供嵌入与入库复用。

## 9. 引用溯源（Grounding）

- 知识片段在 Prompt 中编号为 `[来源1] [来源2] ...`；
- 系统提示要求 LLM 引用时标注 `[来源N]`；
- 回答同时返回 `sources` 元数据（文档名、分块序号、相似度、片段预览），前端可折叠展示。

**效果**：用户可逐条核对回答依据，LLM 幻觉被极大约束。

## 10. 检索质量评估（本项目观测结果）

以「可口可乐含糖量高吗，糖尿病人能喝吗」为例：

| 方法 | Top1 结果 | 说明 |
|------|-----------|------|
| 纯 BM25 | 可口可乐 | 字面命中 |
| 混合检索(RRF) | 可口可乐 / 零度可口可乐 / 佳得乐 | 语义扩展更丰富 |
| + 重排 | 可口可乐优先，其余相关性排序 | 交叉编码器校正 |

> 知识库检索接口 `/api/knowledge/search` 可直接调试任意 query 的召回质量。

## 11. 性能优化记录

| 环节 | 优化 | 效果 |
|------|------|------|
| 启动 | 模型惰性加载 + 后台预热 | 服务秒级可用 |
| 检索 | 向量化 BM25 + FAISS 精确索引 | 单次检索 < 10ms |
| 嵌入 | 批量 + GPU + LRU 缓存 | 100 块入库 < 1s |
| 重排 | 仅对小候选集（6条）打分 | 控制延迟 |
| 前端 | Vue 路由级代码分割 | 首屏 < 100KB gzip |
